# Как участвовать в WM OS

Спасибо за интерес. Проект ранний (`0.1.0`), поэтому особенно ценны небольшие
проверяемые изменения: исправление сборки, тесты, честные состояния UI и документация.

## 1. Требования

* JDK 17.
* Android SDK с platform 35 и build-tools.
* Gradle 8.9.
* Windows/PowerShell — основная среда разработки, но проект не привязан к ОС.

`local.properties` с `sdk.dir` создаётся локально и **не коммитится**.

## 2. Сборка и тесты

Целевые команды:

```powershell
gradlew.bat :app:assembleDebug
gradlew.bat :app:testDebugUnitTest
```

Gradle Wrapper зафиксирован в дереве (`gradlew.bat`, `gradlew`, `gradle/wrapper/`, версия 8.9).
Не меняйте версию wrapper без обсуждения.

Не запускайте сборку параллельно с другой сборкой в том же каталоге. Перед Pull Request
убедитесь, что:

* `:app:assembleDebug` завершился `BUILD SUCCESSFUL`;
* `:app:testDebugUnitTest` зелёный;
* в diff нет секретов, `local.properties`, `build/`, `.gradle/`, баз и логов.

## 3. Стиль кода

* Официальный Kotlin code style, 4 пробела, trailing comma.
* Стиль проверяется ktlint (`org.jlleitschuh.gradle.ktlint`, CLI 1.2.1):

  ```powershell
  gradlew.bat :app:ktlintCheck     # гейт, падает на новых нарушениях
  gradlew.bat :app:ktlintFormat    # автоформатирование
  ```

  Существующие нарушения зафиксированы в `app/ktlint-baseline.xml`. Baseline нужно
  **уменьшать**, а не пополнять: если правите файл — приводьте его к нулю нарушений.
  Перегенерировать baseline допустимо только при осознанном изменении правил
  (`gradlew.bat :app:ktlintGenerateBaseline`), и это должно быть видно в диффе.
* Имена типов/функций/переменных — английские; пользовательские строки — русские.
* Без wildcard-import'ов.
* Публичные API и неочевидные решения — с KDoc на русском или английском (в проекте
  встречаются оба; придерживайтесь языка файла).
* Compose:
  * состояние поднимайте наверх, экран не должен сам создавать репозитории;
  * собирайте состояние через `StateFlow` + `collectAsStateWithLifecycle()`;
  * не выполняйте блокирующий I/O в композиции и на Main;
  * для длинных списков — `LazyColumn`, не `Column` + `forEach`.
* Не добавляйте «кнопку-заглушку». Если функция не реализована, покажите текст/disabled
  или не показывайте элемент вовсе.
* Ошибки пользователю — по-русски, с конкретным следующим шагом.

## 4. Архитектурные правила

```text
Compose → ViewModel → Repository → DAO → Room
```

* Бизнес-правила и валидация — в репозиториях (`data/repo`), не в DAO и не в Compose.
* Чистая логика без Android — в `domain/` и покрывается unit-тестами.
* ViewModel получает зависимости через `CreationExtras.container()` и фабрику.
* Новые зависимости добавляйте в `AppContainer` лениво; не создавайте второй контейнер.
* Не добавляйте Hilt/Koin без отдельного обсуждения: текущий граф намеренно ручной.
* Не обращайтесь к `AppContainer` из композиции. Единственное существующее исключение —
  выбор папки в `NoteEditorScreen`; новые экраны должны идти через ViewModel.
* Сетевые/файловые операции — только `withContext(Dispatchers.IO)` или в репозитории
  на `Dispatchers.IO`.
* AI-инструменты не получают SQL, файловые пути, shell и произвольный код.
* Мутирующий инструмент обязан иметь `prepare()` + `commit()` + подтверждение в UI.

## 5. Тесты

* Unit-тесты: `app/src/test/java/dev/wmos/domain/`.
* Для новой логики повторений/парсера/калькулятора добавляйте тест в существующий класс
  или новый рядом.
* Room-тесты — через `room-testing` и `Robolectric` (зависимости уже есть).
* Compose UI-тесты — `androidTest`, `createAndroidComposeRule`.
* Для исправления бага сначала добавьте падающий тест, если это возможно без Android-
  эмулятора.
* Не удаляйте существующие тесты, чтобы «позеленить» сборку.

## 6. Изменения схемы БД и миграции

Сейчас `WmDatabase` имеет `version = 1` и **не** использует
`fallbackToDestructiveMigration()`. Любое изменение схемы — это отдельная работа:

1. Измените `Entities.kt` (и DAO/запросы, если нужно).
2. Увеличьте `version` в `@Database`.
3. Напишите `Migration(oldVersion, newVersion)` с явным SQL:
   `CREATE TABLE`, `ALTER TABLE`, backfill, `DROP` — по необходимости.
4. Зарегистрируйте миграцию в `WmDatabase.build()`:
   `.addMigrations(MIGRATION_1_2)` (сейчас списка нет).
5. Убедитесь, что KSP экспортирует схему в `app/schemas`
   (`room.schemaLocation` уже настроен).
6. Добавьте тест миграции через `MigrationTestHelper`.
7. Проверьте обновление на копии реальной базы, а не только на чистой установке.

Запрещено:

* добавлять `fallbackToDestructiveMigration()`;
* менять тип/имя колонки без миграции;
* удалять таблицу с пользовательскими данными без явного решения и теста.

## 7. Добавление инструмента Грауса

1. Добавьте схему в `ToolRegistry.definitions` (типы, описания, `required`,
   `additionalProperties = false`).
2. Решите, мутирующий ли он. Если да — добавьте имя в `isMutating()`.
3. Для read-only: реализуйте ветку в `execute()`.
4. Для мутирующего: `prepare()` (валидация без записи) + `commit()` (запись и повторное
   чтение) + ветка в `execute()` не нужна.
5. Пишите `action_log` с фактическим статусом и `targetIds`.
6. Не добавляйте доступ к SQL/файлам/shell.
7. Обновите `docs/AI_TOOLS.md` и добавьте тест (валидация аргументов, успех, ошибка).

## 8. Добавление экрана и маршрута

1. Объявите маршрут в `ui/nav/Routes.kt`.
2. Добавьте `composable(...)` в `ui/nav/WmApp.kt`.
3. Экран не должен знать `NavController`: передавайте колбэки `onBack`, `onOpen…`.
4. ViewModel + `Factory`; при параметрах — `fun factory(id: String)`.
5. Нижняя навигация показывается только для пяти верхнеуровневых маршрутов; detail-экраны
   её не показывают.
6. Для списков используйте `EmptyState` с полезным CTA, для ошибок — сообщение и retry.
7. Проверьте Back, поворот экрана и потерю ввода.

## 9. Секреты и приватность

* Никогда не коммитьте реальные API-ключи, keystore, `.env`, `local.properties`.
* В тестах — только фиктивные значения (`sk-test-...`).
* Не логируйте заметки, чаты, ключи, токены, Authorization-заголовки и содержимое файлов.
* Не добавляйте аналитику/рекламные SDK без отдельного обсуждения.
* Новые сетевые вызовы — только HTTPS; не отключайте проверку сертификатов.
* Если ключ случайно попал в Git — считайте его скомпрометированным, отзовите и
  замените; удаления коммита недостаточно.

## 10. Коммиты

Используйте Conventional Commits, английские тип/scope, русское или английское тело:

```text
feat(reminders): add monthly skip policy tests
fix(ai): move Graus HTTP call off the main thread
docs(backup): describe current JSON export
refactor(data): extract folder cycle guard
test(parser): cover time range clarification
chore(build): add Gradle wrapper 8.9
```

Правила:

* один логический change set на коммит;
* не смешивайте форматирование и поведение;
* в теле объясняйте «почему», если изменение неочевидно;
* ссылайтесь на issue, если он есть.

## 11. Pull Request

В описании укажите:

* что изменено и зачем;
* какие файлы затронуты;
* как проверяли (команды, устройства, API);
* что **не** проверено;
* есть ли миграция/изменение формата;
* скриншоты для UI-изменений.

Чек-лист:

- [ ] сборка проходит;
- [ ] unit-тесты проходят;
- [ ] новые тесты добавлены (или объяснено, почему нет);
- [ ] нет секретов и приватных данных;
- [ ] обновлена документация (`README`, `docs/*`, `CHANGELOG`);
- [ ] destructive actions имеют точные подтверждения;
- [ ] нет фиктивных кнопок и ложного «Готово»;
- [ ] ошибки не теряют введённый текст.

## 12. Сообщения об уязвимостях

Не открывайте публичный issue с эксплойтом или ключом. Используйте приватный
GitHub Security Advisory или свяжитесь с мейнтейнером. Подробности — в `SECURITY.md`.
