# Напоминания WM OS

Документ описывает фактические правила повторения, разбор естественных фраз, планирование
через `AlarmManager`, уведомления и восстановление расписания. Исходники:
`domain/reminder/Recurrence.kt`, `domain/reminder/NaturalReminderParser.kt`,
`domain/reminder/ReminderScheduler.kt`, `data/repo/ReminderRepository.kt`,
`reminders/Reminders.kt`, `ui/screens/reminder/*`.

## 1. Сущность и статусы

Напоминание — отдельная таблица `reminders`, а не поле задачи. У него есть:

* `nextTriggerAt` — ближайшее срабатывание (epoch millis UTC);
* `timeZoneId` — IANA-зона, в которой пользователь задал местное время;
* `recurrenceRule` — JSON-правило или `null`;
* `status`, `notificationId`, `revision`, `lastFiredAt`;
* `linkedEntityId` / `linkedEntityType` — логическая связь, в UI не заполняется.

| Статус | Значение |
|---|---|
| `SCHEDULED` | Запись сохранена, будильник поставлен (точно или неточно) |
| `NOT_SCHEDULED` | Запись сохранена, но будильник поставить не удалось |
| `SNOOZED` | Отложено; `nextTriggerAt` — время нового сигнала |
| `FIRED` | Сигнал сработал, пользователь ещё не выполнил действие |
| `DONE` | Выполнено; для серии — пользователь завершил текущее срабатывание |
| `CANCELLED` | Отменено без удаления записи |
| `MISSED` | Время прошло, серия не может быть пересчитана (например, одиночное) |

Активными для `rescheduleAll()` считаются `SCHEDULED`, `SNOOZED` и `NOT_SCHEDULED`.

## 2. Схема `RecurrenceRule`

`RecurrenceRule` сериализуется kotlinx.serialization в JSON и хранится в
`reminders.recurrenceRule`.

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `frequency` | `DAILY` / `WEEKLY` / `MONTHLY` | — | Частота |
| `interval` | Int | `1` | Шаг; в UI всегда 1, но схема поддерживает больше |
| `daysOfWeek` | Set<Int> | `emptySet()` | ISO: Пн=1 … Вс=7; только для `WEEKLY` |
| `dayOfMonth` | Int? | `null` | 1..31; только для `MONTHLY` |
| `monthlyPolicy` | `CLAMP_TO_LAST_DAY` / `SKIP` | `CLAMP_TO_LAST_DAY` | Поведение для отсутствующего числа |
| `hour` | Int | `9` | Местный час |
| `minute` | Int | `0` | Местная минута |

Пример:

```json
{
  "frequency": "MONTHLY",
  "interval": 1,
  "daysOfWeek": [],
  "dayOfMonth": 31,
  "monthlyPolicy": "CLAMP_TO_LAST_DAY",
  "hour": 9,
  "minute": 0
}
```

`encode()` использует `encodeDefaults = true`, `decode()` — `ignoreUnknownKeys = true` и
возвращает `null` при повреждённом JSON, а не бросает исключение.

## 3. Арифметика повторений

Точка входа — `RecurrenceCalculator.nextAfter(rule, anchor, after)`: вернуть **строго после**
`after` следующий момент или `null`, если его не удалось найти.

### 3.1 DAILY

```text
step = max(1, interval)
candidate = atTime(дата after в зоне anchor, rule)
если candidate <= after: candidate = atTime(дата candidate + step, rule)
повторять, пока candidate <= after (защита 4000 итераций)
```

Важно: `interval > 1` отсчитывается от даты `after`, а не от исходного `anchor`.
Поэтому «каждые 2 дня» при запросе в другой день может сместиться по чётности.
В UI и парсере `interval` всегда 1, так что это проявляется только при ручном JSON/будущем API.

### 3.2 WEEKLY

```text
days = daysOfWeek, либо день недели anchor, если набор пуст
anchorWeek = понедельник недели anchor
cursor = дата after в зоне anchor
до 400 дней:
    candidate = atTime(cursor, rule)
    если candidate > after и день недели входит в days:
        weekStart = понедельник недели cursor
        weeks = WEEKS.between(anchorWeek, weekStart)
        если weeks % step == 0 → вернуть candidate
    cursor += 1 день
```

В отличие от DAILY, чётность `interval` для WEEKLY привязана к неделе anchor.
Если `daysOfWeek` пуст, используется день недели anchor.

### 3.3 MONTHLY

```text
step = max(1, interval)
targetDay = dayOfMonth ?: день месяца anchor
month = месяц after в зоне anchor
до 120 месяцев:
    length = длина месяца
    если targetDay <= length: day = targetDay
    иначе если policy == CLAMP_TO_LAST_DAY: day = length
    иначе day = -1 (пропуск)
    если day > 0 и candidate > after → вернуть candidate
    month += step
```

Следствия:

* 31-е в 30-дневном месяце при `CLAMP_TO_LAST_DAY` срабатывает 30-го;
* при `SKIP` такой месяц пропускается целиком;
* 29 февраля в невисокосный год при `CLAMP_TO_LAST_DAY` срабатывает 28 февраля;
* `interval > 1` отсчитывается от месяца `after`, а не от месяца anchor.

Поведение для 29/30/31 числа:

| `dayOfMonth` | `CLAMP_TO_LAST_DAY` | `SKIP` |
|---|---|---|
| 29 | В феврале невисокосного года — 28-е; в остальные месяцы — 29-е | Февраль невисокосного года пропускается |
| 30 | В феврале — последний день (28/29); в остальные месяцы — 30-е | Февраль пропускается, 30-е остаётся в 30-дневных месяцах |
| 31 | В 30-дневных месяцах — 30-е, в феврале — 28/29; иначе 31-е | Пропускаются все месяцы, где нет 31-го (февраль, апрель, июнь, сентябрь, ноябрь) |

Года как отдельной единицы повторения нет: правило не «каждый год», а «каждый месяц».
29 февраля поэтому обрабатывается как месячное правило, а не как годовая дата.

### 3.4 DST и часовой пояс

`atTime()` строит `ZonedDateTime.of(LocalDate, LocalTime, zone)`. Для перехода на летнее
время Java-время само разрешает gap/overlap: несуществующее местное время сдвигается вперёд,
неоднозначное выбирает более ранний offset. Отдельной политики WM OS нет.

Известное ограничение: в `nextDaily`/`nextWeekly`/`nextMonthly` вызов
`RecurrenceCalculator.atTime(date, rule)` идёт **без аргумента `zone`**, поэтому по умолчанию
используется `ZoneId.systemDefault()`, а не зона напоминания. Даты при этом итерируются
в зоне anchor, а время собирается в зоне устройства. Если зона напоминания отличается от
текущей зоны телефона (поездка, ручная смена зоны), результат может отличаться от ожидаемого.
`ReminderRepository.nextOccurrence()` передаёт anchor/after в зоне напоминания, но это
ограничение калькулятора всё равно срабатывает.

Тест на DST проверяет только ежедневное 09:00 в `Europe/Berlin` через переход 29 марта
(время 09:00 не попадает в gap). Тестов на gap/overlap в 02:30–03:30 нет.

Отдельный fallback: `NaturalReminderParser.firstOccurrence()` при неудачном поиске
первого срабатывания (дневной/недельный/месячный цикл) возвращает **следующий
понедельник** в то же время. Это страховка парсера; в обычных сценариях она не
срабатывает, но может дать неожиданную дату для вырожденного правила.

## 4. Естественно-языковой разбор

`NaturalReminderParser.parse(rawText, now)` нормализует строку: trim, нижний регистр,
`ё → е`, схлопывание пробелов. Разбор идёт по шагам, каждый найденный фрагмент вырезается.

### 4.1 Что реально поддерживается

| Фраза / шаблон | Результат | Пример |
|---|---|---|
| `через N минут` / `мин` | Один раз, `now + N минут` | «через 45 минут» |
| `через N часов` / `час` / `ч` | Один раз, `now + N часов` | «через 2 часа» |
| `через N дней` / `день` / `дня` | Один раз, `now + N дней`, секунды/нано обнуляются | «через 3 дня» |
| `в HH` / `в HH:MM` / `к HH` | Один раз; без даты — сегодня или завтра | «в 18:30», «к 9» |
| `утра` / `вечера` / `дня` / `ночи` после часа | Коррекция часа | «в 8 вечера» → 20:00 |
| `сегодня`, `завтра`, `послезавтра` | Дата | «завтра в 18:30» |
| `каждый день` / `каждую день` | DAILY, время 09:00 по умолчанию | «каждый день в 09:00» |
| `каждый <день недели>` / `каждую <день недели>` | WEEKLY с одним днём | «каждый понедельник в 10:00» |
| `каждую неделю` | WEEKLY без явных дней (день anchor) | «каждую неделю в 10:00» |
| `каждое N число` / `каждый N-е число` | MONTHLY, N = 1..31 | «каждое 15 число в 12:00» |

Дни недели: `понедельник/пн`, `вторник/вт`, `среда/среду/ср`, `четверг/чт`,
`пятница/пятницу/пт`, `суббота/субботу/сб`, `воскресенье/вс`.

Заголовок собирается из оставшегося текста: удаляются ведущие «напомни», «напомнить»,
«напоминание», «создай напоминание», «поставь напоминание», схлопываются пробелы,
обрезаются `, . - —`, первый символ делается заглавным. Если ничего не осталось,
возвращается исходная строка целиком. Поскольку нормализация идёт в нижний регистр,
исходный регистр слов (кроме первого) и буква «ё» в заголовке теряются.

### 4.2 Неоднозначные фразы

Парсер **не придумывает** время:

* `вечером`, `утром`, `днём`, `ночью` без точного часа → `NeedsClarification`
  («… — это неоднозначно. Укажите точное время, например 18:30»);
* «завтра купить билеты» (дата без времени) → `NeedsClarification`
  («Дата есть, а время не указано…»);
* «с 10 до 12 разобрать почту» → `NeedsClarification`, потому что не выбрано начало или конец;
* фраза без даты/времени → `NoDate`.

Особый случай: «в 09:00» без даты, если 09:00 уже прошло, переносится на завтра.
Если дата указана явно («сегодня в 09:00», а сейчас 14:00), парсер вернёт `Success`
с временем в прошлом и warning'ом «Указанное время уже прошло…». Сохранить такое
напоминание нельзя: `ReminderRepository.create()` отклонит `triggerAtMillis <= now`.

### 4.3 Чего парсер не понимает

* «в пятницу», «в следующий вторник» — день недели без слова «каждый»;
* «через неделю», «через месяц», «через полчаса», «через час с небольшим»;
* «25.12», «25 декабря», «в конце месяца», «по будням», «каждые 2 недели»;
* несколько дней недели в одной фразе: «каждый вторник и четверг» даст WEEKLY только
  на вторник, а «и четверг» останется в заголовке;
* «в 18.30» с точкой, «18:30» без предлога «в»/«к»;
* диапазоны и «до/после обеда»;
* любой interval > 1, все дни месяца, кроме одного числа.

## 5. Сохранение и планирование

### 5.1 Создание

```text
title.trim().isNotEmpty()                 иначе ошибка
triggerAtMillis > System.currentTimeMillis()  иначе «Время напоминания уже прошло»
notificationId = abs(id.hashCode()) % 100_000 + 1000
INSERT reminder (status = SCHEDULED)
scheduler.schedule(...)
если FAILED → UPDATE status = NOT_SCHEDULED
```

Сохранение двухфазное: сначала строка, затем будильник. Если Android отказал, запись
остаётся, но статус честно становится `NOT_SCHEDULED`. Репозиторий возвращает
`ReminderSaveResult(reminderId, scheduling, nextTriggerAt)`.

`notificationId` — обычно в диапазоне 1000..100999 (это хеш UUID, а не гарантированно
уникальный счётчик); возможны коллизии, хотя и маловероятные.

### 5.2 Редактирование

`update()`:

1. находит существующую запись;
2. отменяет старый будильник и уведомление;
3. увеличивает `revision`, ставит `SCHEDULED`;
4. сохраняет и планирует заново с тем же `notificationId`;
5. при `FAILED` ставит `NOT_SCHEDULED`.

Проверки «время в будущем» в репозитории нет — её делает UI редактора. Прямой вызов
`update()` с прошлым временем возможен.

### 5.3 Завершение (`complete`)

* одиночное напоминание → `DONE`, будильник отменён;
* серия → вычисляется следующее срабатывание от `nextTriggerAt`, запись получает
  `nextTriggerAt = next`, `SCHEDULED`, `lastFiredAt = now`, `revision + 1`, будильник
  ставится заново;
* если следующего нет → `DONE`;
* если планирование нового не удалось → `NOT_SCHEDULED`; при этом запись откатывается
  к **старому** `nextTriggerAt` (используется `existing.copy(...)`, а не `updated`).

Завершение одного экземпляра не завершает серию, если следующее срабатывание вычислимо.

### 5.4 Откладывание (`snooze`)

```text
until = now + minutes (по умолчанию 10)
cancel(старый alarm)
nextTriggerAt = until
status = SNOOZED
revision += 1
schedule(until)
если FAILED → status = NOT_SCHEDULED, Result.failure
```

Правило серии не меняется. Но после того как отложенный сигнал сработает, `ReminderReceiver`
только помечает `FIRED`, записывает occurrence и показывает уведомление. Он **не**
пересчитывает следующее срабатывание серии. Серия продолжится только если пользователь
нажмёт «Выполнено» (`complete()`), который посчитает следующее от текущего `nextTriggerAt`
(то есть от времени snooze, а не от исходного расписания). Если просто закрыть уведомление,
серия останется в `FIRED`.

### 5.5 Отмена и удаление

* `cancel()` — отменяет будильник/уведомление, ставит `CANCELLED`, строка остаётся;
* `delete()` — отменяет будильник/уведомление и физически удаляет строку.

## 6. Точные и неточные будильники

`AlarmReminderScheduler` использует `AlarmManager.RTC_WAKEUP`.

| Условие | Метод | Результат |
|---|---|---|
| `Build.VERSION.SDK_INT >= S` и `canScheduleExactAlarms()` | `setExactAndAllowWhileIdle` | `EXACT` |
| точные запрещены / API < S | `setAndAllowWhileIdle` | `INEXACT` + сообщение о задержке |
| нет `AlarmManager` | — | `FAILED`, «Системный сервис будильника недоступен» |
| `SecurityException` | — | `FAILED`, «Нет разрешения на точный будильник» |
| `IllegalArgumentException` | — | `FAILED`, текст исключения |

На API < 31 точные будильники разрешены всегда. В манифесте объявлен
`SCHEDULE_EXACT_ALARM`; `USE_EXACT_ALARM` нет. Разрешение на точные будильники
не запрашивается автоматически: редактор показывает карточку и ведёт в системные
настройки `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`.

`ReminderScheduler` — интерфейс с `schedule`, `cancel`, `canScheduleExact`,
`notificationsEnabled`. Реализация — `AlarmReminderScheduler`; другая реализация
(например, для тестов) в коде отсутствует.

## 7. Уведомления

Канал создаётся в `WmApplication.onCreate()`:

| Параметр | Значение |
|---|---|
| ID | `wm_reminders_v1` |
| Название | «Напоминания» |
| Важность | `IMPORTANCE_HIGH` |
| Видимость на lock screen | `VISIBILITY_PRIVATE` |
| Вибрация | включена |

`canPost()`:

* Android 13+ — проверка `POST_NOTIFICATIONS`;
* ниже — `NotificationManagerCompat.areNotificationsEnabled()`.

Если уведомления запрещены, `show()` молча возвращает управление; запись при этом
может иметь статус `SCHEDULED`/`NOT_SCHEDULED` в зависимости от того, что ответил
`AlarmManager`, а не от разрешения на уведомления. Редактор напоминания запрашивает
`POST_NOTIFICATIONS` при открытии экрана (Android 13+) и показывает карточку
«Уведомления выключены» со ссылкой в настройки.

Уведомление содержит:

* заголовок и описание (BigText);
* действия «Выполнено» и «Отложить на 10 минут»;
* content intent на `MainActivity` с `EXTRA_REMINDER_ID`.

**Ограничение:** `MainActivity` не читает `EXTRA_REMINDER_ID` и не выполняет deep link
на конкретное напоминание. Нажатие на уведомление открывает приложение на «Главной»,
а не редактор этого напоминания.

## 8. Приём сигнала и действия

`ReminderReceiver` — `exported=false`, работа в `goAsync()` + `CoroutineScope(IO)`:

| Action | Поведение |
|---|---|
| нет action (будильник) | `markFired` → `recordOccurrence(..., "FIRED")` → показать уведомление |
| `ACTION_DONE` | `complete(id)` → отменить уведомление |
| `ACTION_SNOOZE` | `snooze(id, 10)` → отменить уведомление |

`recordOccurrence` создаёт строку `reminder_occurrences` с `state = "FIRED"`, `firedAt = null`,
`ID = UUID`. Идемпотентной защиты нет: повторное срабатывание или повторное нажатие
создаст новую occurrence/повторно выполнит `complete`.

## 9. Восстановление после reboot / update / смены зоны

`BootReceiver` (`exported=true`) слушает:

* `BOOT_COMPLETED`;
* `MY_PACKAGE_REPLACED`;
* `TIMEZONE_CHANGED`;
* `TIME_SET` (`Intent.ACTION_TIME_CHANGED`).

Он вызывает `ReminderRepository.rescheduleAll()`:

```text
для каждого напоминания в SCHEDULED/SNOOZED/NOT_SCHEDULED:
    target = nextTriggerAt
    если target <= now:
        если есть правило: next = nextOccurrence(...)
            если next != null: target = next, status = SCHEDULED, revision += 1
            иначе: status = MISSED, пропустить
    schedule(target)
    FAILED → status = NOT_SCHEDULED
вернуть число поставленных (EXACT + INEXACT)
```

Свойства:

* база — источник истины, поэтому повторный вызов не создаёт дубликаты: тот же
  `notificationId` даёт тот же `PendingIntent` request code, и `AlarmManager` заменяет
  существующий будильник;
* одиночное напоминание, время которого прошло, помечается `MISSED` и больше не планируется;
* для серии следующее считается от старого `nextTriggerAt`, а не от «сейчас + интервал»;
* `rescheduleAll` не вызывается при простом открытии приложения — только по broadcast;
* `WorkManager` для напоминаний не используется (зависимость объявлена, но в коде
  напоминаний не задействована).

## 10. Редактор напоминания

`ReminderEditorScreen` поддерживает два режима:

* **«Текстом»** — поле natural text, живой preview (title, дата/время, warnings,
  уточняющий вопрос или «время не распознано»);
* **«Вручную»** — title, description, дата (чипы «Сегодня/Завтра/+7 дней» и ввод),
  время (диалог часы/минуты), повтор (`Один раз`, `Каждый день`, `По дням недели`,
  `Каждый месяц`), дни недели для WEEKLY.

Ручной режим всегда сохраняет `allDay = false` и `timeZoneId = ZoneId.systemDefault().id`.
Правило собирается так:

| Выбор | Правило |
|---|---|
| Один раз | `null` |
| Каждый день | `DAILY`, время из формы |
| По дням недели | `WEEKLY`, выбранные дни; если пусто — текущий день |
| Каждый месяц | `MONTHLY`, день = день выбранной даты |

Для серии `resolvedTrigger()` берёт `firstOccurrence(rule, now)`. Для одиночного —
проверяет, что время в будущем; иначе сохращение отклоняется сообщением
«Укажите корректное будущее время напоминания».

После сохранения показывается фактический результат планирования:

| Precision | Карточка |
|---|---|
| `EXACT` | «Запланировано» |
| `INEXACT` | «Запланировано неточно» + причина |
| `FAILED` | «Сохранено, но не запланировано» + причина |

## 11. Тесты и пробелы

Есть 12 unit-тестов `RecurrenceCalculatorTest` и 11 `NaturalReminderParserTest`:

* daily same/next day, weekly next/same weekday, every two weeks;
* monthly CLAMP для 31-го, SKIP для 31-го, 29 февраля;
* DST-переход (только 09:00), encode/decode, мусорный JSON;
* «завтра в 18:30», «через 45 минут», «каждый понедельник», «каждый день»,
  «вечером» → clarification, прошедшее время → завтра, дата без времени,
  фраза без даты, диапазон, «каждое 15 число», «в 8 вечера».

Чего нет:

* тестов `AlarmManager`, `ReminderReceiver`, `BootReceiver`, каналов и разрешений;
* тестов DST-gap/overlap и смены часового пояса;
* тестов snooze-серии и повторного срабатывания;
* тестов на 29/30/31 через естественный парсер (только калькулятор);
* тестов идемпотентности и коллизий `notificationId`;
* обработки `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`;
* deep link из уведомления в конкретное напоминание;
* all-day напоминаний (поле есть, UI всегда `false`).
